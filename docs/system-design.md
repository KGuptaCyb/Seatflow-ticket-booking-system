# System design (742 words)

Seatflow is a monolithic web application designed for correctness around the one resource that cannot be oversold: an event seat. The browser is a React/Vite single-page application. Express exposes JSON APIs, Prisma maps those APIs to PostgreSQL, Redis/BullMQ schedules expiry work, and Socket.IO broadcasts changes to browsers viewing the same event. A monolith keeps deployment and evaluation simple while retaining clear boundaries between HTTP routes, persistence, jobs, and real-time delivery.

The relational model separates a reusable venue `Seat` from an `EventSeat`. A venue seat contains physical row, number, category, and optional layout coordinates. An event creates one EventSeat per venue seat, capturing its price and mutable status. This lets one theatre layout host many events without allowing a booking for one screening to affect another. `Booking` owns immutable commercial data (reference, purchaser, total, status), while `BookingSeat` joins a booking to its EventSeat and has a unique `eventSeatId`; a seat therefore cannot appear in two bookings. Waitlist and WaitlistOffer model a customer’s category-specific place in line and any time-bound offer. Offers are retained as history, so an expired offer can advance the same seat to the next customer.

The state machine is `AVAILABLE → HELD → BOOKED`, with `AVAILABLE → OFFERED → HELD` for waitlist allocation. Holds include an owner and expiry time. On a hold request, PostgreSQL locks all requested EventSeat rows with `SELECT … FOR UPDATE`, validates that all are available (or releases a stale hold), and updates them together. The whole request fails if even one seat is not available. The booking route repeats the lock and verifies the current user owns a non-expired hold before atomically creating the booking, booking seats, and switching EventSeats to `BOOKED`. The database lock serializes competing requests; unique constraints provide a second line of defence. Transaction timeouts are intentionally increased to 15 seconds because lock waits can legitimately occur under contention.

After a hold is stored, BullMQ schedules a delayed job keyed by seat and expiry. The worker conditionally releases only a seat still held beyond that specific expiry, which makes retries harmless. The worker then attempts waitlist allocation. Socket.IO broadcasts every hold, booking, release, offer, and expiry to an event room. The client initially loads a seat snapshot and merges event updates, which gives responsive visual state without treating the client as authoritative.

Cancellation changes the booking to `CANCELLED`, releases its EventSeats, emits availability, and calls `offerNext` for each released seat. `offerNext` locks the seat and the oldest active, matching-category waitlist row in one transaction. It makes the seat `OFFERED`, creates an offer token with a configured expiry, and schedules another BullMQ job. An accept request locks offer, waitlist, and seat together; it only succeeds while the offer is pending, unexpired, owned by the caller, and the seat remains offered. It converts that offer into a standard customer-owned hold. If an offer job wins first, it marks the offer expired, returns the seat to available, and continues FIFO allocation. These conditional transitions handle duplicate jobs and concurrent accept/expiry safely.

QR tickets are generated only after a booking transaction commits. The QR payload is a public URL constructed from `PUBLIC_FRONTEND_URL` and the booking reference, so any camera can open a login-free verification page. The data URL is persisted when possible and regenerated on My Tickets for older confirmed bookings. The API calls Resend over HTTPS with the QR embedded and attached as a PNG when `RESEND_API_KEY` and `EMAIL_FROM` are configured. Email failure is logged, not allowed to undo a confirmed booking; the ticket remains retrievable in the application. Keys stay in server-only environment variables.

JWTs carry user id, email, and role. Middleware authenticates requests, then authorizes customer, organiser, or admin actions. Organisers can retrieve summaries only for their events; admins can manage venues and review all summaries. Revenue is computed from confirmed booking totals, excluding cancellations.

For production, deploy the React static bundle separately from the API, use managed PostgreSQL and Redis, configure exact CORS origins, TLS Redis URLs where required, strong rotating JWT secrets, verified Resend domains, health checks, logs, and a worker process. The next scaling step would split the BullMQ worker from API instances and add email retry/outbox records, while retaining PostgreSQL row locks as the source of truth.
